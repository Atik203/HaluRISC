# Research Project Blueprint: Explainable Hallucination Risk Prediction via Classical ML

### Core Idea

A high-speed, single-pass hallucination detection system that bypasses expensive "LLM-as-a-judge" mechanisms. By treating the target LLM as a black box, this system extracts linguistic and structural features (e.g., hedging frequency, entity density, lexical overlap) directly from the text. These features are fed into lightweight classical ML ensembles (XGBoost, Random Forest) to produce a real-time hallucination risk score. Crucially, the system uses SHAP (SHapley Additive exPlanations) to provide human-readable justifications for its predictions, delivered through a modern interactive React frontend.

### 0. Research Design Decisions & Assumptions

* **Assumption 1 (The Black-Box Hypothesis):** Hallucinations leave statistical and linguistic "fingerprints" in the output text (e.g., unnatural length, lack of citations, sudden semantic shifts) that can be isolated without needing the model’s internal token probabilities.
* **Assumption 2 (Compute Efficiency):** Supervised tree-based models will achieve an $F_1$ score comparable to large neural evaluators while reducing computational overhead (FLOPs) and latency by an order of magnitude.
* **Decision 1:** The system will strictly utilize single-pass extraction. Multi-sampling (asking the LLM the same prompt 5 times) will not be used, as it defeats the goal of real-time, low-cost detection.
* **Decision 2:** The core pipeline will run entirely on local environments (like a WSL-based Miniconda setup) to ensure high reproducibility and isolated dependency management for peer review.

### 1. Literature Review & Novelty Contribution

Recent 2025–2026 literature demonstrates a strong shift toward classical machine learning for hallucination detection. Studies utilizing the HaluEval benchmark have proven that multi-signal approaches—combining lexical overlap, entity coverage, and semantic similarity—can allow classical classifiers to achieve $F_1$ scores exceeding 0.92. However, most current solutions still lack real-time user explainability. This research bridges that gap by coupling an XGBoost classifier with SHAP visualizations, delivering a high-accuracy, low-latency system that explicitly tells the user *why* a text is flagged.

### 2. Research Motivation

As LLMs are integrated into critical domains, hallucinations remain a primary barrier to trust. Current mitigation strategies rely on computationally expensive sampling-based consistency checks or secondary LLM validation loops. These approaches are slow, API-cost-heavy, and opaque. Real-world applications require an instantaneous, cheap, and verifiable layer of trust before presenting an AI response to an end-user.

### 3. Problem Statement

How can we accurately detect factual hallucinations in LLM outputs in real-time, utilizing only a single text pass, while maintaining high classification accuracy ($F_1 > 0.75$) and providing transparent, interpretable feature attributions for the calculated risk?

### 4. Complete System Pipeline Architecture

The system operates sequentially via a microservice architecture:

1. **Input Layer:** A user submits a Query + Context + LLM Answer via the React frontend.
2. **Feature Extraction Layer (Python API):** Extracts structural, semantic, and linguistic features from the text.
3. **Classification Layer:** An optimized XGBoost/CatBoost model ingests the feature vector and outputs a probability score $P(Hallucination)$.
4. **Explainability Layer:** The SHAP TreeExplainer computes the marginal contribution of each feature to the final score.
5. **Presentation Layer:** The API returns a JSON payload to the frontend, dynamically rendering a "Trust Gauge" (0-100%) and a bar chart of the SHAP values.

### 5. Detailed Feature Extraction Strategy

To achieve high accuracy without deep neural processing, the feature vector must be highly descriptive. The system will extract:

* **Structural Markers:** Sentence count, token length, and punctuation density (hallucinations often exhibit overly complex or unnaturally uniform sentence lengths).
* **Information Density:** Named Entity Recognition (NER) counts via standard NLP libraries. A mismatch between prompt entities and response entities strongly signals hallucination.
* **Linguistic Uncertainty:** Frequency analysis against a curated lexicon of hedging terms (e.g., "might", "possibly", "I believe").
* **Semantic Consistency:** Cosine similarity between the prompt and response embeddings to measure contextual drift.

### 6. Mathematical Formulation

The hallucination risk is framed as a binary classification problem where $y \in \{0, 1\}$. The feature extraction function $\phi(x)$ maps the input text $x$ to a feature vector $\mathbf{v} \in \mathbb{R}^d$.
The ensemble model predicts the probability:


$$P(y=1 \vert{} \mathbf{v}) = \sigma \left( \sum_{k=1}^{K} f_k(\mathbf{v}) \right)$$


*(Where $K$ is the number of trees, $f_k$ is the weight of the $k$-th tree, and $\sigma$ is the sigmoid function).*
SHAP values $\phi_i$ are then computed to explain the output $f(\mathbf{v})$ relative to the baseline $E[f(\mathbf{v})]$:


$$f(\mathbf{v}) = E[f(\mathbf{v})] + \sum_{i=1}^{d} \phi_i$$

### 7. Models & Tools

* **Backend Core:** Python 3.10+, `scikit-learn`, `xgboost`, `catboost`.
* **NLP Processing:** `spaCy` (for rapid NER and POS tagging), `nltk` (for lexical analysis).
* **Explainability:** `shap` (SHapley Additive exPlanations).
* **API & Serving:** FastAPI, `uvicorn` (for asynchronous requests and high throughput).
* **Frontend UI:** React, TypeScript, Recharts (for SHAP visualizations and risk gauges).

### 8. Dataset Plan

The primary training and validation environment will be the **HaluEval Benchmark**, which provides high-quality, large-scale labeled examples.

* **Task-Specific Splits:** Question Answering, Dialogue, and Summarization subsets. These are balanced (50% hallucinated, 50% factual).
* **General User Queries:** Human-annotated samples reflecting a realistic, imbalanced prior (~18% hallucination rate).

### 9. Evaluation Strategy

Because the general dataset is imbalanced, raw accuracy is an invalid metric. The classifier will be evaluated using:

* **Primary Classification Metrics:** Precision, Recall, and $F_1$-score.
* **Robustness Metrics:** Area Under the Receiver Operating Characteristic (AUROC) and the Matthews Correlation Coefficient ($MCC$).
* **Efficiency Metrics:** End-to-end inference latency (in milliseconds) compared against a heavy LLM-as-a-judge baseline.

### 10. Edge Cases & Failure Handling

* **Ultra-Short Responses:** If an LLM answers with "Yes" or "No", feature extraction vectors will be too sparse. *Mitigation:* The API will implement a minimum token threshold, returning a "Not Enough Data" state to the frontend.
* **Confident Fabrication:** LLMs can occasionally state profound falsehoods with highly definitive language (zero hedging). *Mitigation:* NER density and Context Overlap features will serve as a counterbalance when linguistic uncertainty fails.

### 11. Risk Assessment

| Risk | Impact | Likelihood | Mitigation Strategy |
| --- | --- | --- | --- |
| **Feature Extraction Bottleneck** | High | Medium | Use optimized C-backed libraries (`spaCy`) instead of heavy deep-learning transformers for standard text parsing. |
| **Overfitting to HaluEval** | High | High | Enforce strict train/test/validation splitting. Ensure hyperparameters (tree depth, $L_2$ regularization) in XGBoost are heavily constrained via cross-validation. |
| **React/API CORS Errors** | Low | High | Pre-configure FastAPI middleware to accept cross-origin requests from the local TypeScript development server. |
