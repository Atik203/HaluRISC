\section{Project Overview}

Large language models (LLMs) like ChatGPT are very good at writing text that sounds confident and correct, but they sometimes generate information that is wrong or made up --- this is called a hallucination. This project builds a complete system that predicts how likely an LLM answer is to be hallucinated. The system is black-box friendly --- it only needs the question, the answer, and (optionally) some context, without ever looking inside the LLM. It is lightweight --- it uses simple text features and classical machine learning (XGBoost), so it runs in milliseconds on a normal computer, with no GPU and no API fees. It is explainable --- for every prediction it shows \emph{why} the answer looks risky (for example: ``the answer contradicts the provided context'', or ``the answer contains numbers that are not supported''). Finally, it is presentable --- a polished, interactive web dashboard lets a judge or supervisor test the system live, type any question and answer, and see the risk score and explanation instantly. The novelty is not in inventing hallucination detection, but in combining NLI-based consistency features, calibrated risk scores, and tested explanations into one lightweight system --- a combination no published work offers as a single product.

\section{Motivation}

LLMs are now used in real products --- chatbots, Q\&A systems, content review tools --- where a wrong answer has a real cost, and the most common way to detect hallucinations is to ask the LLM itself to judge its own output \cite{selfcheck}, which is slow, expensive, and sometimes wrong. A lightweight model trained on simple text features (word overlap, named entities, contradiction with context, numbers, hedging words) can flag risky answers almost instantly and at almost zero cost. A risk score is also more useful than a simple ``yes/no'' flag, because real systems can decide what to do with a risky answer --- show a warning, ask for human review, or fetch better evidence. And because the final result is a working product with a clean UI rather than just a report, the project is fully ready for live demonstration.

\section{Objectives}

Research question: Can a lightweight machine learning model predict hallucination risk in LLM answers using simple text features, while giving calibrated risk scores and clear explanations? To answer this, the project has five objectives: (1) build a feature extraction pipeline (about 20--30 features) that captures how well an answer agrees with the question and context --- word overlap, named entities, contradiction signals, numbers, hedging words, and semantic similarity; (2) train and honestly compare classical models --- a simple heuristic baseline, Logistic Regression, Random Forest, and XGBoost; (3) calibrate the risk scores so that a score of 0.8 truly means ``about 80\% risk'', making the score trustworthy for real use; (4) explain predictions with SHAP, giving a global view of which features matter most plus detailed case studies of individual predictions; and (5) build a polished web dashboard (React + FastAPI) with strong UI/UX --- live prediction, risk gauge, explanation panel, and a demo gallery --- designed for presentation and judging.

\section{Related Work}

Hallucination detection is an active research area. The most common approach asks the LLM itself to judge its own answer, as in SelfCheckGPT \cite{selfcheck}, but this is slow and expensive. To cut this cost, small language models have been used as detectors \cite{haluagent}, and lightweight evaluation models such as Luna \cite{luna} show that efficient detection is possible in practice. Other approaches train neural classifiers on frozen language encoders \cite{ieeeTai}, or combine explainable text signals with machine learning \cite{ijert,multimedia}.

On the benchmark side, HaluEval \cite{haluEval} and TruthfulQA \cite{truthqa} provide standard test beds, and fine-grained methods such as FActScore \cite{factscore} evaluate factual precision in detail. Newer benchmarks such as FaithBench \cite{faithbench} show that current detectors still fail on challenging cases, and SpikeScore \cite{spikescore} shows that cross-domain generalization remains an open problem.

None of these works combine lightweight engineered features with calibrated risk scores, tested explanations, and a deployable dashboard --- this is the gap the project fills.

\section{Methodology}

The pipeline has seven clear steps:

\begin{enumerate}
    \item Data preparation --- load the HaluEval QA dataset, clean the text, and manually inspect 50 random samples to verify label quality before training.
    \item Feature extraction --- compute features in seven groups: length/style, lexical overlap, entity overlap, NLI contradiction (using a lightweight pre-trained NLI model), numeric consistency, hedging phrases, and semantic similarity.
    \item Model training --- 5-fold stratified cross-validation, hyperparameter tuning for XGBoost, and every experiment repeated with 3 random seeds, reported as mean $\pm$ standard deviation.
    \item Model comparison --- heuristic baseline, Logistic Regression, Random Forest, and XGBoost, judged on F1, AUROC, precision, recall, and MCC.
    \item Calibration --- apply Platt scaling to the final model \cite{costeff} and measure the gain with Expected Calibration Error (ECE) and Brier score.
    \item Explanation --- SHAP global feature importance plus 3 local case studies; error analysis on 20 wrong predictions (10 false positives, 10 false negatives).
    \item Deployment --- FastAPI backend serving the trained model, and a React (Vite) dashboard with a clean, modern UI: risk gauge, feature breakdown, and live input panel.
\end{enumerate}

Statistical rigor: model differences are tested with McNemar's test and bootstrap confidence intervals, so conclusions are not based on chance from a single split.

External comparison: results are compared with published HaluEval detection baselines, such as SelfCheckGPT \cite{selfcheck}, so a judge can see whether the scores are good or bad.

\section{Dataset}

We use the HaluEval benchmark \cite{haluEval} (EMNLP 2023) --- the standard dataset for hallucination evaluation, widely used and well documented.

\begin{itemize}
    \item Size: 35{,}000 samples across 4 task types (QA, dialogue, summarization, general).
    \item Used here: the QA subset (about 10{,}000 samples). Each sample has a question, an answer, a context, and a label (hallucinated or not).
    \item Why QA: it is the largest, cleanest, and most comparable subset, and it matches the demo scenario (question $\rightarrow$ answer $\rightarrow$ risk score).
\end{itemize}

One limitation to note: most HaluEval samples were generated by ChatGPT, so results will be framed as performance on the HaluEval benchmark rather than as general hallucination detection performance.

\section{Expected Results}

Based on published baselines on the same benchmark \cite{haluEval,ieeeTai}, we expect the tuned XGBoost model to reach an F1 score of around 0.75--0.85 and an AUROC of around 0.80--0.90 on the QA subset. Success means matching or beating these baselines while keeping the system lightweight, explainable, and ready for live demonstration.

The project will deliver:

\begin{enumerate}
\item A trained, calibrated XGBoost model with feature ablation and SHAP explanations.
\item Statistical significance tests (McNemar, bootstrap confidence intervals).
\item A polished, judge-ready web dashboard --- live risk prediction with clean UI/UX.
\item Reproducible code: dataset preparation, feature extraction, training, and API.
\end{enumerate}

\section{Project Plan}

The project runs in two phases: experiments in the first half, product in the second. Weeks 1--4 cover data preparation, feature extraction, model comparison, and calibration. Weeks 5--8 cover SHAP explanations and error analysis, the FastAPI backend, the React dashboard, and the final report and demo.
